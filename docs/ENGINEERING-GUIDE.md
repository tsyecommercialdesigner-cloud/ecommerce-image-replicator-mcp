# MCP Server 工程与 CI/CD 规范

本指南维护开发、验证、GitHub CI/CD 与版本控制细则；安装、启动、凭据和 Host 配置见 [手册与交付规范](MANUAL-WRITING-GUIDE.md)。它是消费项目的工程要求，不代表本模板仓库已为业务项目建立或运行流水线。实际工作流、检查命令和权限须在消费仓库落地并验证。

按改动读取：需求与架构见第 1 节，依赖及验证收尾见第 2 节，流水线与发布见第 3–4 节，Git 跟踪见第 5 节；能力设计、权限、副作用及 Skill 协作见第 6 节。跨范围变更同时读取相关章节。

## 1. 规范、架构与任务

- 用户要求和项目规范定义预期行为，源码、锁文件与检查结果说明实际状态；不一致时报告差异，不把现有缺陷改写成需求。
- 采用 spec-kit 时，先读 `.specify/memory/constitution.md`、当前 `specs/<feature>/` 中的 `spec.md`、`plan.md`、`tasks.md` 及涉及的 `contracts/`；路径、命令以实际版本和 Agent 集成为准。缺失不等于已完成，未经任务授权不初始化或重建已有资料。
- spec 写目标、范围、场景、边界与可测试验收；plan 记录技术决策并检查项目原则，保留用户指定约束；tasks 关联实现和验证。按项目流程完成澄清、方案、任务、实现和验收，小型修正不机械重走全流程。
- 变更同步相关规范、契约、任务、测试与文档，验收项关联证据并区分通过、失败、不适用、未验证。采用 Beads 等系统时关联 issue 与任务标识，明确唯一任务状态来源，避免双份进度矛盾。
- 不固定业务产品、能力数量或外部接口。Python 保留 `src/<module_name>/` 等既有布局；其他技术栈不引入无关依赖。项目名、发行包、模块、服务标识和安装路径的映射按手册定义。
- 默认采用对应语言的官方 MCP SDK v2，并核对锁定版本接口与可用性；Python 服务类/导入及模块入口均须按实际版本验证，不能仅复制 API 示例。SDK 版本、协议版本、传输及 Host 兼容范围分别记录，既有版本迁移单独验证，不由模板自动升级。

## 2. 依赖、构建与本地验证

- Python 包操作用 uv，不用裸 `pip install`，不以 `requirements.txt` 替代既定的 `pyproject.toml` 与 `uv.lock`。开发初始化 `uv sync --locked`，成员运行安装按手册裁剪开发组；新项目默认 hatchling，已有后端按实际维护。
- Node.js 默认 `npm ci` 复现 `package-lock.json`；已有其他包管理器时保留对应锁与等效流程。运行包放 `dependencies`，构建/测试工具放 `devDependencies`；从源码安装的 TypeScript 项目先安装构建工具再构建，不假定被 Git 忽略的 `dist/` 会随 clone 到达。
- 运行时及包管理器支持范围写入项目元数据和版本文件；CI 使用明确版本。依赖声明、锁、构建配置共同维护，不以删锁、浮动升级或自动改用全局包修复失败。
- 维护者提供真实存在、失败即非零退出的格式、lint、类型检查、测试、构建和协议检查入口，CI 与本地共用。按技术栈选择工具，未使用的检查说明原因，不创建空壳成功脚本或用 `--if-present` 掩盖必需脚本缺失。
- 根据需求覆盖单元、契约和集成验证；遵从已启用的测试优先原则。测试框架按项目选型，例如 unittest 项目可用 `uv run --no-sync python -m unittest discover -s tests`，不把它作为全部项目的固定命令。
- 协议检查用实际 SDK 客户端/Inspector，匹配锁定协议的初始化或请求元数据要求；覆盖适用能力发现、输入/输出 schema、权限与错误返回。能力契约及失败路径按第 6 节分层验收；配置验收见手册第 5 节，不以配置解析或进程启动代替协议及业务成功。
- 默认用无真实权限的测试值和受控替身验证上游映射，不把它说成真实业务成功。CI 协议检查不得自动触发收费/写入功能；真实 Host 或上游验证单独授权并记录环境、命令、结果与未覆盖项。
- 文档修改检查链接、示例解析、参数和模板一致性；不为修改规范而安装业务环境或改动用户 Host。验证在隔离目录执行，不清理维护者的真实环境。
- 测试前明确工作目录和临时资源范围，优先使用工作目录内独立且已忽略的临时子目录。平台或工具确需系统临时目录等外部位置时，记录本次创建的路径及清理方式；不向无关目录散落测试文件。
- 测试结束后先归档必要且已脱敏的证据，包括版本、命令、结果、退出码及必要的失败日志，关联任务并记录归档位置；本地放在工作目录内约定位置，CI 使用设定保留期限的 artifacts。证据不得含秘密或用户私有数据，归档不等于自动提交 Git 或发布。
- 证据归档后及时停止本次测试进程并清理本次创建的临时文件、环境与资源，复查外部临时路径无遗留；成功、失败或中断均通过清理钩子（如 `finally`、Shell trap 或 CI 始终执行的收尾步骤）落实。仅清理本次拥有的资源，保留用户环境、测试源码、fixtures 和归档证据；清理失败须报告遗留路径、原因及后续处理，不宣称清理完成。

## 3. GitHub CI 与合并门禁

所有消费项目采用 PR 驱动的 CI/CD；项目创建或迁移时交付实际 `.github/workflows/` 配置及本地复现入口。下表规定流水线行为，不是可以直接提交的通用 YAML；具体工具、平台、版本和命令由消费项目填写。

| 阶段 | 触发与必需行为 |
|---|---|
| PR CI | `pull_request`：锁定安装，运行相关格式/lint/类型检查、测试、构建、秘密扫描、依赖风险检查及无收费副作用的协议检查；仅在明确不适用时省略对应项并记录依据。 |
| 默认分支 CI | 合并后针对实际合入提交复验；缓存不是验证证据，失败不能被此前的 PR 结果覆盖。 |
| 发布 CD | 受控版本标签或批准的发布入口：确认目标提交已通过必需检查，构建/验证对应发行物并自动发布 GitHub Release、包或镜像等项目实际交付物；源码安装项目至少交付版本标签、发布记录与该标签的安装验收结果。 |
| 部署 CD | 仅远程服务适用：将同一已验证产物逐级部署，按环境审批、执行健康及协议检查，失败停止并按已验证方案回滚。纯本地 stdio 项目将服务端部署标为不适用，CD 仍负责版本发布。 |

- 在 GitHub 分支保护或 ruleset 中要求 PR、实际 CI 状态检查及评审；默认分支名按仓库设置，不硬编码 `main`。门禁检查名称稳定；路径过滤、跳过任务或仅有工作流文件不能证明门禁已生效。账号/仓库权限或套餐无法启用时明确报告限制，不宣称已配置。
- 在声明支持的平台和运行时上安排必要矩阵，至少覆盖成员主要平台。测试结果、覆盖率和构建报告作为有保留期限的 Actions artifacts 上传；覆盖率门槛取项目验收约定，不强制统一数字。
- 从干净 checkout 验证完整安装：Python 无开发依赖运行；需要构建的 Node 项目执行锁定安装与构建，验证运行依赖声明不依赖全局或祖先目录。安装/更新的真实命令见手册第 3 节。
- 对文档变更运行相应轻量检查；改变安装、依赖、构建或工作流时必须触发相关实际检查。不得删除失败测试、降低验收标准或标记必需步骤 `continue-on-error` 来通过 CI。
- 能力、schema、权限或副作用变更触发第 6 节相关契约与安全回归；声明支持 Skill 协作时补充对应组合验证。CI 使用受控替身或测试环境，不授予生产写权限来补齐验收。
- Git/PR/标签/发布操作遵从当前授权与仓库策略；流水线设计不能自行授予 Agent 提交、推送、合并或生产发布权限。评审与 CI 通过后才允许按既定授权合入或发布。

## 4. 工作流安全与发布追溯

- 默认 `GITHUB_TOKEN` 只读，按 job 授予必要权限；仅发布 job 获得对应写权限。秘密经 GitHub Secrets、受保护环境或适用 OIDC 提供，不写入 YAML、日志、缓存或 artifacts；普通测试使用假值。
- 外部/分叉 PR 不接触生产秘密或发布权限；不在高权限 `pull_request_target` 或 `workflow_run` 中 checkout 并执行不可信 PR 代码或产物。标题、分支名等外部输入通过安全参数/环境变量处理，不拼入可执行脚本。
- 第三方 Actions 固定到核对过来源的完整提交 SHA；采用平台工作流依赖锁机制时按其实际版本验证。依赖和 Actions 更新通过可评审 PR，不自动跟随浮动标签升级。缓存按系统、工具版本与锁标识隔离，不缓存凭据或私有配置。
- 发布记录关联 tag、完整 Git SHA、元数据版本、CI 运行与安装/协议验收结果；包、镜像等产物提供校验摘要及项目适用的来源证明。发布标签受保护，不覆盖已发布版本；远程部署复用已验证产物，避免逐环境无依据重建。
- 失败停止发布；给出撤回版本、切回已知良好版本、恢复运行及数据兼容性限制。保留成员 `.env` 和私有数据，不以 `reset --hard`、`clean -fdx` 或清空安装目录进行默认升级/回滚。
- GitHub 仓库及已验证版本是默认成员来源；源码获取、私有仓库认证、安装构建与升级步骤见手册。不强制提供本地 ZIP 打包脚本；需要 ZIP 时另按手册第 9 节验收。

## 5. Git 跟踪与 `.gitignore`

复用 [根目录 `.gitignore` 模板](../.gitignore) 时先合并项目现有规则，按实际技术栈删减并核对例外；不要覆盖已有配置。模板只忽略可重建或私有状态，不是发布清单或秘密扫描器。

| 应跟踪 | 应忽略 |
|---|---|
| 源码、测试源码、安全 fixtures、可复现示例 | 虚拟环境、`node_modules/`、包/工具缓存 |
| 元数据、依赖锁、运行时版本声明、构建配置 | 编译输出、临时包、测试结果、覆盖率、基准报告 |
| `.github/workflows/`、共享脚本、规范/方案/契约、手册 | 日志、临时文件、运行 PID、本地运行数据与秘密 |
| 空密钥 `.env.example`、无秘密的 Host/Agent 模板 | 真实 `.env` 及变体/备份、私有配置、认证与会话状态 |

模板补齐下列常见工具产物；采用该工具时让输出落到已声明位置，未使用的工具规则可按项目删减。自定义生成目录须补充精确规则，不以扩大文件后缀范围代替用途判断。

| 用途 | 代表规则及作用域 |
|---|---|
| 脚本、类型与前端工具缓存 | 原有 Python/Node 缓存，以及 `.pyre/`、`.dmypy.json`、`.vite/`、`.vitest/`。 |
| 覆盖率临时数据及报告 | `.coverage`、`.coverage.*`、`.nyc_output/`、`htmlcov/`、`coverage/`、`coverage.xml`、`lcov.info`。 |
| 测试和浏览器测试报告 | `junit.xml`、`junit-*.xml`、`pytest.xml`、`test-results/`、`test-reports/`、`playwright-report/`、`blob-report/`、`allure-results/`、`allure-report/`。 |
| 基准与变异测试产物 | `.benchmarks/`、`benchmark-results/`、`.mutmut-cache`；`/mutants/` 仅用于项目根目录的生成代码。 |

上述未以 `/` 开头的测试／缓存规则同时覆盖项目根与嵌套子项目，例如 `packages/server/coverage.xml` 和 `packages/server/test-results/`；构建与本地数据规则仍保持各自的既定作用域。测试源码、输入 fixtures、golden 文件和快照应与生成物分开存放。必须跟踪的安全 fixture 若恰好命中报告名或通用日志规则，先检查其内容，再为具体路径添加最窄反向规则；若父目录已被忽略，还须按 Git 规则精确放行必要父目录。不得整体放行测试目录而重新引入秘密或缓存。

- 不忽略整个 `tests/`、`test/`、`fixtures/`，不通过 `*.test.*`、`test_*.py` 等规则排除测试源码；包含真实数据或秘密的测试资料先脱敏，敏感原件仅留私有位置。
- 不用 `*.json`、`*.yaml`、`*.lock`、`*.db`、`*.zip` 等宽泛规则代替目录/用途判断：它们可能是配置、锁或测试 fixtures。运行数据库放在已忽略的本地数据目录，固定测试库按需跟踪。
- `output/` 默认是可重建产物；`outputs/` 不整体忽略，正式维护的模板/产物仍需跟踪。构建输出默认不跟踪；若部署确需受控提交生成物，写明依据并调整规则，CI 校验源码与产物一致，不能依赖维护者未提交的 `dist/`。
- 不整体忽略 `.specify/`、`specs/` 或共享 `.agents/`、`.claude/`、`.codex/`；仅忽略明确的本地状态和秘密。Beads 等工具的库、导出和同步文件按其自身规则维护。
- 用 `git check-ignore -v --no-index -- <path>` 检查来源规则，用 `git ls-files` 核对已跟踪文件；同时验证秘密/缓存被忽略、测试/锁/指南/工作流/空示例仍可跟踪。忽略规则不追溯移除已跟踪文件或历史秘密，发现泄露按凭据处置流程处理。
- 修改规则后在临时 Git 仓库验证正反例，避免借用维护仓库自身的忽略规则：顶层和嵌套子项目的生成物应被忽略；Python/Node 测试源码、安全 JSON/YAML/数据库/归档 fixtures、快照、依赖锁、CI 与共享 Host 配置应仍可跟踪。特殊 fixture 的精确例外也需验证，且不能放开其他日志、秘密或缓存。
- 不为应用忽略规则而删除文件；调整跟踪状态前先核对影响及授权。Git 忽略与 ZIP/镜像的排除清单独立验收，不能用 `.gitignore` 证明发布物不含秘密。

## 6. 能力契约与运行边界

### 6.1 职责与能力设计

| 层次 | 负责的内容 |
|---|---|
| MCP Server | 通过协议提供实际支持的 Tools、Resources、Prompts 等能力，落实接口校验、业务授权和可核验的执行结果；未实现的能力不声明。 |
| Skill（适用时） | 围绕任务结果组织触发条件、步骤、参数选择、判断分支及验收，详细规则和样例按需引用。 |
| Agent 与 Host | 按实际宿主机制发现与选择能力、加载资料、调度调用和处理权限交互；记录兼容范围。 |
| 执行环境与外部系统 | 落实身份、权限、文件/网络隔离、资源限额与审计；MCP 协议本身不提供这些保证。 |

- 按稳定职责设计可复用工具，写清用途、不适用场景及副作用，避免同义工具造成误选；不以工具数量作为设计目标。聚合计算、事务或必须保持的操作顺序可由服务端封装，无需拆成大量细碎调用。
- 任务 SOP、报告模板与团队方法按需放入 Skill 或业务文档，不塞入每个工具描述。业务授权、合法状态转换与数据约束留在服务端代码；不得以“Skill 会先检查”替代服务端校验。
- 使用已有工具即可完成任务时不强制新增 Server 或 Skill。Skill 可调用宿主工具或脚本；组合边界由实际需求决定，不将 MCP 当作唯一执行途径。

### 6.2 接口契约与兼容性

- 每项能力明确标识、用途、输入、输出、错误、权限及副作用。工具参数说明类型、必填/默认、枚举、范围和单位，字段名与 schema 以锁定 SDK/协议为准；`inputSchema`、`outputSchema` 等协议字段不能照搬其他工具格式的拼写。描述与实际校验保持一致。
- 区分请求结构/协议错误与工具执行失败，按 SDK/协议返回；可反馈给模型纠正的工具执行失败使用 `isError: true`，不以成功文本掩盖失败。适用时声明结构化输出并校验；部分结果标明缺失范围与原因，不冒充完整成功。
- 声明必需与可选上游能力及版本/权限条件；调用前通过受支持的发现或检查入口确认可用性。缺失、拒绝或不兼容时明确受影响步骤，不猜测标识，不静默切换数据源或扩大权限。
- MCP 工具名与 Host 暴露给模型的名称分别记录，按实际机制消除同名工具歧义；不假定所有 Host 都使用 `ServerName:tool_name`。适配资料只引用权威契约，避免在多个 Skill 复制维护 schema。
- 服务、SDK、协议、Host 及适用 Skill 版本分别记录。破坏性 schema、权限或语义变化提供迁移及回归依据；能力缺失与未验证项如实披露，不由服务单侧通过推断全部宿主兼容。

### 6.3 权限与信任边界

- 按身份与任务授予最小权限，读取与写入分开；校验请求对象的访问权限，而非仅凭工具可发现或名称在允许清单内就放行。Skill 指令、工具描述与安全注解均不能代替实际授权。
- `allowed-tools` 的支持、语法及限制/预授权效果由 Host 决定，不能当成跨宿主的硬白名单或沙箱。核对服务账号、上游令牌范围和执行环境；权限拒绝后不得改用 Shell、脚本、直接 API 或另一工具绕过限制。
- 文件访问校验允许根目录、规范化路径及符号链接/重解析点逃逸；URL/下载校验目标、重定向及未授权网络访问。外部文档、工具结果和错误消息按数据处理，不作为新的指令或授权；输入不拼入可执行代码。
- 本地 stdio 按实际运行账号限制文件、网络和子进程权限。项目另有 HTTP 服务时，服务端另落实 Origin 校验、认证、TLS 及访问控制；采用令牌时校验受众和权限，不将客户端令牌不经验证地透传下游。此项不扩展成员手册仅提供本地 stdio 接入的范围。

### 6.4 副作用、状态与恢复

- 明确查询与写入/通知/扣费等操作的区别，以及调用前提、授权范围、成功凭据和部分失败行为。生成草稿不等于获准发送，计划通过不等于已执行；重复确认按当前授权和项目策略判断，不机械增加审批。
- 必须可靠执行的顺序、审批和检查用代码、状态机、受控工作流或外部系统机制落实；Skill 的 SOP 用于指导，不能保证必经步骤不会被跳过。并发修改需要版本检查、条件写入或适用事务，不依赖先读后写的口头约定。
- 按操作定义超时、取消、重试条件与上限；对写入说明幂等键/去重、状态查询及适用补偿机制。请求超时或结果不明时先查询状态，不能直接重放；取消请求不等于撤销已经发生的副作用。上游不支持恢复或幂等时明确限制并采取保守处理。
- 多步操作记录可恢复状态、已完成步骤和外部操作标识，避免重复副作用；只记录必要且脱敏的信息，不声称能够自动回滚不可逆操作。

### 6.5 结果来源与上下文控制

- 大量数据在有能力的上游或服务端筛选、分页、聚合，并设置响应大小、并发和资源预算；不一次返回完整日志或数据库，不静默截断关键结果。返回续取方式或明确截断/覆盖范围。
- 对时效敏感的数据保留必要来源、查询范围、采集时间与分页/聚合口径；区分实时、缓存、替身及缺失数据。摘要保留可追溯依据，减少返回量不能牺牲结论核验。
- Skill 协作资料以简短能力索引和相对路径按需引用契约、样例及限制，不在工具描述中加载整套业务手册；不假定所有 Host 都支持动态工具发现或相同的上下文加载方式。

### 6.6 分层验收与证据

按受影响能力选择以下检查，并按第 2 节归档证据及清理；未启用的能力或协作项说明不适用原因，不为满足表格创建无关组件。

| 层次 | 验收重点与结论边界 |
|---|---|
| 契约与实现 | 输入合法/非法/空值/边界，输出与错误语义，上游映射、分页及预算；受控替身不能证明真实上游成功。 |
| 协议与权限 | 通过实际 SDK 客户端验证适用能力发现和访问；覆盖同名能力消歧、缺依赖、权限拒绝、越界及恶意返回数据。 |
| 状态与副作用 | 超时后状态不明、重复调用、取消、部分失败、并发和中断恢复；在受控环境确认不会重复写入或突破授权。 |
| Host/Skill 协作 | 对声明支持的实际版本验证工具标识、参数映射、数据来源与流程完成条件；有 Skill 时增加选择、步骤及失败分支，不将工具成功等同任务成功。 |

- 证据关联需求/契约、版本、环境、命令或调用、预期与实际结果及未覆盖项，区分静态检查、隔离测试、真实 Host 与真实业务验证。权限控制需有实际拒绝证据，不能只展示配置字段；不得为测试绕过授权。
